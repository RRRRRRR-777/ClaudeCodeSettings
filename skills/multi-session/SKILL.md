# multi-session: 並列セッションオーケストレーション

複数の独立Claude Codeセッションをコーディネーター1セッションが統括する運用の手順書。実践から抽出した手順と落とし穴を定義。

## 用語

- **コーディネーター**: 本skillを実行するセッション。委任・承認伝達・マージ等の集約点
- **ワーカー**: 実作業を行う独立セッション。ユーザーが別ターミナルで起動
- **cross-session messaging**: `ListAgents`（発見）+ `SendMessage`（送信）によるセッション間通信

## Agent vs 独立セッションの使い分け

独立セッション選択の基準（いずれか該当時）:

- レートリミット分散必要（サブエージェントは親セッションの上限を共有、独立セッションは別枠）
- ユーザーが各作業に直接介入したい（ワーカーはinteractiveセッションとしてユーザーと対話可能）
- 作業が長時間・大規模でセッション単位の永続性・再開性が欲しい

該当しなければAgentツール（サブエージェント）で足りる。サブエージェントもSendMessage対象になるが、親のコンテキスト・利用上限に依存する。

## ライフサイクル

### 1. 起動（2段階方式）

一括で「起動＝即着手」させない。起動確認と本指示を分離 → ユーザーが起動直後に構成を調整できる。

1. コーディネーターが**起動プロンプト**を作成しユーザーへ渡す（雛形: `details/templates.md`）。内容は「作業に着手せず、名前と対象だけ返答して待機」の指示のみ
2. ユーザーが別ターミナルでセッション起動・命名（`--name`フラグ or `/rename`）。命名規則: `#{チケット番号} {チケットタイトル}`（先頭・最重要チケットを代表とする）
3. コーディネーターが`ListAgents`で発見確認
4. `SendMessage`で**本指示**を送信（雛形: `details/templates.md`）。ここで初めて着手

### 2. 本指示に必ず含める項目

- 対象タスク・チケット（複数まとめる場合は特別運用である旨を明記）
- 完了条件の**逐語**引き渡し（ワーカーは会話文脈を引き継がない）
- ブランチ名・worktree作成指示・ベース情報（cloudId等）
- 不変条件（mainを動かさない／マージしない／作業範囲外への破壊的操作禁止）
- 停止基準（プロジェクトのworkflow規約の人間ゲート・自動昇格条件を参照）
- **「AskUserQuestionを使わない。ユーザー確認が必要な論点は必ずSendMessageでコーディネーターへ送る」の明記** — ワーカーがbgセッション内で直接質問すると、その画面を開いていない限り誰にも見えず、質問はdialogExpiry（既定5分）で失効する。質問中はSendMessageも受信できず（not reachable）、コーディネーターからは原因不明の停止に見える（実例あり）
- **「返信は必ずSendMessageで行う」の明記** — ワーカーがプレーンテキスト出力で応答すると届かず、無応答に見える事故が起きる（実例あり）
- 完了時の報告内容（PR番号・検証結果の一次情報）

### 3. 進捗確認・催促

- 状況確認は`SendMessage`で送る。急ぎでなければ「作業の区切りで構わない」と添える
- 一定時間無応答 → 生存確認を送る。それでも無応答なら原因は判別不能（後述の落とし穴参照）、ユーザーへ画面確認を依頼
- ワーカーからの報告はコーディネーターが要約してユーザーへ共有。**ツール結果の転記でなく自分のテキストで**（extractorはツール出力を読めない）

### 4. 判断エスカレーション・承認伝達

- ワーカーは停止基準該当時に作業を止めコーディネーターへ確認を送ってくる
- コーディネーターの一存で承認できない事項（人間ゲート・不可逆操作・スコープ拡大）は`AskUserQuestion`でユーザーに確認
- 複数ワーカーから同時に確認が届いたら、まずテキストで整理・共有してから質問。1ワーカー=1質問グループに分ける（ユーザーがセッション単位で判断できる）
- 回答は各ワーカーへ個別に`SendMessage`で伝達。**伝達後、ワーカーの次の報告で承認が反映されているか確認する** — 承認が届いてもワーカーのコンテキストから抜け落ちる事故がある（実例あり）。矛盾を見つけたら逐語で再送
- 原則: ピア（他セッション）はユーザーの承認を代行できない。ワーカーが「ユーザー本人の明示指示が必要」と拒否した場合（例: Ultracode opt-in）、それは正しい判断。ユーザーに直接その旨を伝え、必要なら各セッションへ直接入力してもらう

### 5. 完了・後片付け・操作分担

- **マージ実行**: コーディネーターが担当。ユーザー最終確認後に`gh pr merge`。マージ前にCI状態を自分で確認（`gh pr view --json mergeable,statusCheckRollup`）
- **prod書き込み・deploy**: コーディネーターが担当（ワーカーには持ち帰り指示を本指示に含める）
- **破壊的コマンド**（docker rm・rm -rf等）: フックでブロックされる環境ではコマンドをユーザーへ提示して委ねる。ワーカー側でブロックされた分もコーディネーターが集約してユーザーへ渡す
- **worktree・ローカルブランチ削除**: コーディネーターで実行可能（`git worktree remove` + `git branch -d`）。ワーカーの「未コミット・未push変更なし」報告を受けてから実施
- ワーカーの完了報告は自己申告のまま受けず、一次情報（PR・CI結果・テストログ）で検証してからユーザーへ報告

## 落とし穴（実測ベース）

1. **`ListAgents`の状態表示は原因を示さない**。idle/busy/waiting/pendingは「メッセージを受け付けられるか」のみ。waiting=ユーザーへ直接確認中の場合もレートリミットの場合もある。状態から原因を断定しない
2. **レートリミットは検知不可**。ワーカー内部のAPI上限エラーはcross-session messagingに一切表れない。`not reachable`+長時間無応答から推測するのみ。確実な確認手段はユーザーによる画面目視だけ
3. **refは変わる**。セッション再接続等で`[ref]`が変化する。送信失敗（not reachable / not an agent）→`ListAgents`で最新ref取得→再送。名前だけで一意ならref省略可、エラーがrefを要求したら付ける
4. **ピア経由の承認は無効**。ユーザーopt-inが必要な機能（Workflow/Ultracode等）は、コーディネーター経由の伝聞では各ワーカーの許可条件を満たさない。ワーカーは拒否するのが正しく、ユーザーの直接入力が必要
5. **プレーンテキスト応答は届かない**。ワーカーが`SendMessage`を使わずテキスト出力すると、コーディネーターには何も届かず無応答に見える。本指示に「返信は必ずSendMessage」を明記して予防
6. **ワーカーの直接質問は誰にも見えない**。bgワーカーがAskUserQuestionでユーザーに直接質問すると、そのセッションの画面を開いていない限り気づけず、dialogExpiryで失効する。質問表示中はSendMessage受信も不能（not reachable）になり、コーディネーターからは停止と区別できない。本指示で「AskUserQuestion禁止・確認はSendMessageでコーディネーター経由」を明記して予防。waiting表示+not reachableの組合せを見たら、ワーカーが直接質問を出している可能性を疑いユーザーへ画面確認を依頼
