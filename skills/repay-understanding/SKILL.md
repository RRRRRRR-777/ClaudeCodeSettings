# 理解負債を返済する

ユーザーがシステムを理解していない状態を、ユーザー自身の理解として取り戻させる。

AI が説明を作ってユーザーが読むだけでは、読んだ直後に分かった気がするだけで定着しない。AI が出した選択肢から選ぶだけでも理解は育たない。理解が残るのは、ユーザーが自分で考えを出し、それと事実とのずれを埋めたときである。この Skill は、先にユーザーが考える問いを1つ置き、その答えと事実のずれを中心に説明する。

## 起動の入口

| 入口 | 判定 | 最初の動き |
|---|---|---|
| ユーザーの依頼 | 「理解したい」「わからない」「どういうこと？」、または `/repay-understanding <対象>` | 「返済の種類」を決めてから手順に進む |
| サインの検出 | 下の表のサインを会話から検出した | 提案だけを行い、同意を得てから「返済の種類」を決める |

検出に使うサインは、会話に表れたものに限る。黙って承認している状態は検出できないので、推測で起動しない。

| サイン | 例 |
|---|---|
| 同じ内容を言い換えて再び質問している | 直前に答えた仕組みを、別の言葉で聞き直している |
| 事実と違う前提で指示や発言をしている | dev と prod が同じ DB だという前提で変更を頼んでいる |
| 直前の説明への戸惑いを示している | 「？」「えっと」「つまり？」 |

サインを検出したときは、作業を中断して教え始めない。誤検出で作業を止めると、ユーザーの負担になるため。`AskUserQuestion` で1回だけ提案する。

- header: `[確認のみ]理解の返済`
- question: ずれていそうな点を1文で示し、この Skill で扱うかを尋ねる
- options: 「いま扱う」と「今はいい」
- 「今はいい」なら元の作業に戻り、同じ点を再び提案しない

ユーザーがすぐに応答できない実行、例えばバックグラウンドやスケジュール実行では、提案せずに完了報告へ1行添える。

## 返済の種類

最初に、理解したい対象が既にあるものか、これから決めるものかを分ける。進み方がまったく違うため。

| 状況 | 進み方 |
|---|---|
| 既にある仕組み・コード・設計・PR・用語を理解したい | 下の「手順」の1から進む |
| これから決める計画や設計を、詰めながら理解したい | Skill ツールで `grilling` を呼び、その進め方に従う。下の「手順」は使わない |

`grilling` は、決めるべきことを問いの木に分け、推奨の答えを添えて1巡ずつ問う。決めるのはユーザーである。既存の仕組みを理解したいときには呼ばない。推奨の答えを選ぶだけになり、理解が育たないため。

`grill-with-docs` と `grill-me` は Claude から呼べない設定になっている。どちらも中身は `grilling` を呼ぶものなので、`grilling` を直接呼ぶ。`grill-with-docs` が併せて呼ぶ `domain-modeling` は呼ばない。用語集や ADR をリポジトリに書くため、返済中はリポジトリを変えないという規則と衝突する。文書に残す場合は、各プロジェクトの慣行に任せる。

## 手順

### 1. 対象を特定し、一次情報を読む

対象は引数 `$ARGUMENTS` または会話から特定する。

説明する前に、対象の一次情報を読む。コード、設計書、PR、設定ファイルなど、事実が書かれている場所である。記憶や一般論から説明すると、誤った説明がそのまま新しい理解負債になるため。

| 対象 | 読むもの |
|---|---|
| 機能・仕組み | 該当するコードの本体と、設計書の該当節 |
| 設計文書 | 文書の全文 |
| PR・Issue | 本文、差分、変更の中心となるファイル |
| 用語 | 設計書・ADR・コードでの使われ方 |
| 直前の説明 | 会話中のその説明と、説明の根拠になったファイル |

ユーザーの既知範囲は、会話から推し量る。分からない場合も追加の質問はしない。手順2の問いへの答えが、既知範囲を知る手がかりになる。

### 2. 先に考える問いを1つ出す

対象の核心について、ユーザーが1〜2行で答えられる問いを1つ出す。

- 例: 「次の20件を取るとき、サーバーは何を手がかりに続きを探していると思いますか？」
- 例: 「解約ボタンを押してから課金が止まるまでに、どのシステムが関わると思いますか？」

問いは `AskUserQuestion` で出す。ただし、選択肢に答えの候補を並べない。答えの候補から選ぶだけでは、ユーザーが自分で考えたことにならないため。答えは「その他」の自由記述で受け取る。

- header: `[確認のみ]先に予想`
- question: 問いの本文と、「答えは『その他』に自由に書いてください」の一文
- options: 「わからない」と「問いを飛ばす」。どちらも説明へ進む

答えに応じて次のように進む。

| 答え | 次の動き |
|---|---|
| 自由記述の答えがある | 手順4で、答えと事実のずれから説明を始める |
| 「わからない」 | 手順3へ進む。問い直しや追加の質問はしない |
| 「問いを飛ばす」 | 手順3へ進む |

次の場合は、この手順を飛ばす。

- 直前の説明が伝わらなかったことへの対応である。ユーザーは既に混乱を示しており、問いを足すと負担が増えるため
- ユーザーがすぐに応答できない実行である

### 3. 説明の手段を1つ選ぶ

表の上の行ほど軽く速い。条件に合う行のうち、最も上のものを選ぶ。

| 状況 | 手段 | 理由 |
|---|---|---|
| 直前の説明が伝わらなかった | 言い直し | 新しい資料を作るより、同じ内容を平易にするほうが早く届く |
| 1つの概念・関数・設定・用語の働き | 会話での説明 | 図のページを作るより速い |
| PR・Issue・長い設計文書、または複数の部品にまたがる流れ | `explain-visually` の図解ページ | 散らばった事実を順に並べ直し、識別子で深掘りできる |
| アーキテクチャ・データモデル・呼び出しの流れを、図1枚で正確に示したい | `d2-diagram` | 図をテキストで持ち、描いた箱と矢印を事実と照合できる |
| ユーザー以外の読み手に渡す説明、またはコードの振る舞いを実行例で確かめながら理解したい | `explainer` の速習資料 | 読み手の既知との差分だけを書き、例と図を道具で検証する |
| 読み終えるのに20分を超える体系的な学習で、章立てや演習が要る | `explainer-book` の学習資料 | 概念の導入順と章ごとの理解度の確かめ方を設計できる |
| 発表やウォークスルーで見せるスライドが要る | `d2-slides` | 図の多い説明を、読む資料ではなく見せる資料にできる |

最初は手段を1つに絞る。足りない部分は、手順5の深掘りで補う。

`explain-visually` 以降の手段は、Skill ツールでその Skill を呼び、対象を引数に渡す。作り方と検証は、呼んだ Skill の手順に従う。`d2-diagram`・`explainer`・`explainer-book`・`d2-slides` は、下の「explainer 系の実行環境」で動かす。

### 4. 説明する

すべての手段に共通する規則は次のとおり。

- 通常の文で書く。出力を簡潔にしたり圧縮したりする指示があっても、返済中の説明には使わない。理解のための説明は、それらの指示自身が全文で書くとしている場面、つまり説明を求められたときや混乱が示されたときに当たる
- 手順2の答えがあれば、答えのどこが合っていて、どこが事実と違うかから始める
- 確認した事実と自分の解釈を分ける。事実には根拠の場所を `path:line` で添える
- 専門用語は初出で一言定義する
- 説明の各項目に識別子を付け、ユーザーが「2をもっと」と指定できるようにする

識別子は、新しい体系を作らずに次のものを使う。

| 説明の形 | 識別子 |
|---|---|
| 会話での説明・言い直し | 項目に `1` `2` `3`、その下に `2-1` |
| explain-visually の図解ページ | ページ内の `D-` `U-` `Q-` と節番号 |
| explainer・explainer-book・d2-slides の資料 | 資料内の節番号・章番号・スライド番号 |
| プロジェクトに既存の識別子がある対象 | その識別子をそのまま使う |

説明の最後には、識別子を指定して深掘りできることを1行で伝える。理解度を確かめるクイズや採点はしない。

#### 言い直しの手順

1. 1〜2文で文脈を置き直す。何の話で、どこまで進んでいたか
2. 短い文で言い直す。1文に1つの内容だけを書き、主語と動作をはっきりさせる
3. 用語はプロジェクトで使われている呼び名に合わせる。設計書・ADR・コードの名前から取り、新しい呼び名を作らない

### 5. 深掘りする

ユーザーが識別子を指定したら、その項目だけを掘り下げる。

- 具体例: 実際のデータや値を使い、処理を通すと何がどう変わるかを示す
- 順序: どの段階で何が起きるかを1ステップずつ示す
- 実際のコード: 該当箇所を引用し、`path:line` を添える
- そうしなかった場合に何が起きるか

資料を作った手段で深掘りする場合は、その Skill の深掘りや改訂の手順に従う。

## explainer 系の実行環境

`d2-diagram`・`explainer`・`explainer-book`・`d2-slides` は、Node 24 以上、d2、npm 依存を前提にする。普段使う Node の版を変えずに動かすため、次の環境で実行する。

| 項目 | 値 |
|---|---|
| Node 24 | `$(ls -d "$HOME"/.nodebrew/node/v24.* \| tail -1)/bin` を PATH の先頭に足す |
| 作業場 | `~/.local/share/repay-understanding/` |
| npm 依存 | 作業場の `node_modules`。`@mizchi/vlmkit`・`marked`・`playwright`・`mermaid` |
| d2 | `d2` コマンド。`d2 layout` に `tala (bundled)` が出ること |

これらの Skill が「リポジトリ」や「資料を置くリポジトリ」と呼ぶ場所は、この作業場に読み替える。読み手のペルソナ `personas/<id>.md`、生成する資料、npm 依存は作業場に置く。資料のディレクトリは必ず作業場の下に作る。スクリプトは資料の場所から上へ `package.json` を探して依存を見つけるので、作業場の外に資料を置くと別のプロジェクトの `package.json` を拾ってしまう。対象のコードや設計書は、元のリポジトリから読むだけにする。プロジェクトのリポジトリに依存やペルソナを置くと、プロジェクトの依存関係と変更履歴が汚れるため。

スクリプトは、作業場をカレントディレクトリにして実行する。

```bash
export PATH="$(ls -d "$HOME"/.nodebrew/node/v24.* | tail -1)/bin:$PATH"
cd "$HOME/.local/share/repay-understanding"
node <skill>/scripts/verify-doc.mjs <doc-dir>
```

Chrome や Playwright のブラウザを起動するコマンドは、Bash のサンドボックスの外で実行する。サンドボックスの中ではブラウザがプロファイルを作れず、起動に失敗するため。

作業場が無い場合は、次の手順で作り直す。

```bash
export PATH="$(ls -d "$HOME"/.nodebrew/node/v24.* | tail -1)/bin:$PATH"
mkdir -p "$HOME/.local/share/repay-understanding"
cd "$HOME/.local/share/repay-understanding"
npm init -y
npm i -D @mizchi/vlmkit marked playwright mermaid
npx playwright install chromium
```

Node 24 が無い場合は `nodebrew install-binary v24` で入れる。普段の版を切り替える `nodebrew use` は実行しない。d2 が無い場合は `brew install d2` で入れる。

## 出力先

ファイルを作るのは、`/tmp/` の下と、explainer 系の作業場だけにする。プロジェクトのリポジトリには書かない。学習記録やレッスンのファイルも作らない。

返済の目的はユーザーの頭の中の理解であり、ファイルではない。リポジトリに説明のファイルが残ると保守の対象が増え、仕様書と取り違えられるおそれもあるため。作業場のペルソナは、次の資料で読み手の既知範囲を再び尋ねずに済ませるために残す。

## やらないこと

- 理解度のクイズや採点
- 説明のための記録やログを、プロジェクトのリポジトリに残すこと
- `domain-modeling` で用語集や ADR を書くこと
- 説明の途中で、対象のコードや設計書を書き換えること
