# 理解負債を返済する

ユーザーがシステムを理解していない状態を、ユーザー自身の理解として取り戻させる。

AI が説明を作ってユーザーが読むだけでは、読んだ直後に分かった気がするだけで定着しない。AI が出した選択肢から選ぶだけでも理解は育たない。理解が残るのは、ユーザーが自分で考えを出し、それと事実とのずれを埋めたときである。この Skill は、先にユーザーが考える問いを1つ置き、その答えと事実のずれを中心に説明する。

## 起動の入口

| 入口 | 判定 | 最初の動き |
|---|---|---|
| ユーザーの依頼 | 「理解したい」「わからない」「どういうこと？」、または `/repay-understanding <対象>` | 手順1から始める |
| サインの検出 | 下の表のサインを会話から検出した | 提案だけを行い、同意を得てから手順1に進む |

検出に使うサインは、会話に表れたものに限る。黙って承認している状態は検出できないので、推測で起動しない。

| サイン | 例 |
|---|---|
| 同じ内容を言い換えて再び質問している | 直前に答えた仕組みを、別の言葉で聞き直している |
| 事実と違う前提で指示や発言をしている | dev と prod が同じ DB だという前提で変更を頼んでいる |
| 直前の説明への戸惑いを示している | 「？」「えっと」「つまり？」 |

サインを検出したときは、作業を中断して教え始めない。誤検出で作業を止めると、ユーザーの負担になるため。`AskUserQuestion` で1回だけ提案する。

- header: `[確認のみ]理解の返済`
- question: ずれていそうな点を1文で示し、この Skill で扱うかを尋ねる
- options: 「いま扱う」と「今はいい」
- 「今はいい」なら元の作業に戻り、同じ点を再び提案しない

ユーザーがすぐに応答できない実行、例えばバックグラウンドやスケジュール実行では、提案せずに完了報告へ1行添える。

## 手順

### 1. 対象を特定し、一次情報を読む

対象は引数 `$ARGUMENTS` または会話から特定する。

説明する前に、対象の一次情報を読む。コード、設計書、PR、設定ファイルなど、事実が書かれている場所である。記憶や一般論から説明すると、誤った説明がそのまま新しい理解負債になるため。

| 対象 | 読むもの |
|---|---|
| 機能・仕組み | 該当するコードの本体と、設計書の該当節 |
| 設計文書 | 文書の全文 |
| PR・Issue | 本文、差分、変更の中心となるファイル |
| 用語 | 設計書・ADR・コードでの使われ方 |
| 直前の説明 | 会話中のその説明と、説明の根拠になったファイル |

ユーザーの既知範囲は、会話から推し量る。分からない場合も追加の質問はしない。手順2の問いへの答えが、既知範囲を知る手がかりになる。

### 2. 先に考える問いを1つ出す

対象の核心について、ユーザーが1〜2行で答えられる問いを1つ出す。

- 例: 「次の20件を取るとき、サーバーは何を手がかりに続きを探していると思いますか？」
- 例: 「解約ボタンを押してから課金が止まるまでに、どのシステムが関わると思いますか？」

問いは `AskUserQuestion` で出す。ただし、選択肢に答えの候補を並べない。答えの候補から選ぶだけでは、ユーザーが自分で考えたことにならないため。答えは「その他」の自由記述で受け取る。

- header: `[確認のみ]先に予想`
- question: 問いの本文と、「答えは『その他』に自由に書いてください」の一文
- options: 「わからない」と「問いを飛ばす」。どちらも説明へ進む

答えに応じて次のように進む。

| 答え | 次の動き |
|---|---|
| 自由記述の答えがある | 手順4で、答えと事実のずれから説明を始める |
| 「わからない」 | 手順3へ進む。問い直しや追加の質問はしない |
| 「問いを飛ばす」 | 手順3へ進む |

次の場合は、この手順を飛ばす。

- 直前の説明が伝わらなかったことへの対応である。ユーザーは既に混乱を示しており、問いを足すと負担が増えるため
- ユーザーがすぐに応答できない実行である

### 3. 説明の手段を1つ選ぶ

| 状況 | 手段 | 理由 |
|---|---|---|
| 直前の説明が伝わらなかった | 言い直し | 新しい資料を作るより、同じ内容を平易にするほうが早く届く |
| 1つの概念・関数・設定・用語の働き | 会話での説明 | 図のページを作るより速い |
| PR・Issue・長い設計文書、または複数の部品にまたがる流れ | explain-visually の図解ページ | 散らばった事実を、理解に必要な順に並べ直す必要がある |

最初は手段を1つに絞る。足りない部分は、手順5の深掘りで補う。

explain-visually を使う場合は、Skill ツールで `explain-visually` を呼び、対象を引数に渡す。ページの作り方と検証は explain-visually の手順に従う。

### 4. 説明する

すべての手段に共通する規則は次のとおり。

- 通常の文で書く。出力を簡潔にしたり圧縮したりする指示があっても、返済中の説明には使わない。理解のための説明は、それらの指示自身が全文で書くとしている場面、つまり説明を求められたときや混乱が示されたときに当たる
- 手順2の答えがあれば、答えのどこが合っていて、どこが事実と違うかから始める
- 確認した事実と自分の解釈を分ける。事実には根拠の場所を `path:line` で添える
- 専門用語は初出で一言定義する
- 説明の各項目に識別子を付け、ユーザーが「2をもっと」と指定できるようにする

識別子は、新しい体系を作らずに次のものを使う。

| 説明の形 | 識別子 |
|---|---|
| 会話での説明・言い直し | 項目に `1` `2` `3`、その下に `2-1` |
| explain-visually の図解ページ | ページ内の `D-` `U-` `Q-` と節番号 |
| プロジェクトに既存の識別子がある対象 | その識別子をそのまま使う |

説明の最後には、識別子を指定して深掘りできることを1行で伝える。理解度を確かめるクイズや採点はしない。

#### 言い直しの手順

1. 1〜2文で文脈を置き直す。何の話で、どこまで進んでいたか
2. 短い文で言い直す。1文に1つの内容だけを書き、主語と動作をはっきりさせる
3. 用語はプロジェクトで使われている呼び名に合わせる。設計書・ADR・コードの名前から取り、新しい呼び名を作らない

### 5. 深掘りする

ユーザーが識別子を指定したら、その項目だけを掘り下げる。

- 具体例: 実際のデータや値を使い、処理を通すと何がどう変わるかを示す
- 順序: どの段階で何が起きるかを1ステップずつ示す
- 実際のコード: 該当箇所を引用し、`path:line` を添える
- そうしなかった場合に何が起きるか

explain-visually のページを深掘りする場合は、explain-visually の「深掘り」の手順に従い、別のページを作る。

## 出力先

ファイルを作るのは `/tmp/` の下だけにする。リポジトリには書かない。学習記録やレッスン、読み手の人物像のファイルも作らない。

返済の目的はユーザーの頭の中の理解であり、ファイルではない。リポジトリに説明のファイルが残ると保守の対象が増え、仕様書と取り違えられるおそれもあるため。

## やらないこと

- 理解度のクイズや採点
- 説明のための記録やログを残すこと
- 説明の途中で、対象のコードや設計書を書き換えること
